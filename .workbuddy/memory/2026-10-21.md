  1. **tie-break 仍反**：`(-count, p)` 平局取字典序最小，要求取最大 ⇒ test_train_bpe 会挂。
  2. **push 压在双层循环最内层**：每个 (pid, pair) 都压一条，每轮几万~几十万条，
     堆会涨到千万级 ⇒ 速度/内存成为新瓶颈。建议把 touched pair 收进 set，本轮结束统一压一次。
  3. **校验循环退出条件分辨不清**「找到了」vs「堆抽空了」，后者会误用过期 max_pair。
  4. count 归零时压入 `(0, p)`，而 `-0 == 0` 会让它通过校验被当成有效 pair。
  5. L46 `if num_pair == 0: break` 一旦触发会终止整个训练（merges 不足）。
- 修法方向：显式记录「本轮是否找到有效 pair」；有效性条件加上「该 pair 在账本里」；
  不要压 count=0 的条目。

## tie-break 修复完成（用户自写，已验收）
- 采用 `Rev` 包装类 + `(-count, Rev(pair))` 双分量键：`class Rev: __init__(self,obj); __lt__ 返回 self.obj > other.obj`。
  `__slots__` 未加（可选，每个对象省 ~100B，OWT 上百万条目 ≈ 100MB）。
- 三处构造必须同形状：L108 建堆 / L62 减计数后 push / L70 加计数后 push；L49、L53 弹出后要 `.obj` 脱壳。
- 混放裸 pair 与 Rev 会 `TypeError: '<' not supported between tuple and Rev` 或 `AttributeError: 'tuple' has no attribute 'obj'`——会响亮崩溃，不会静默。
- 结果：tests/test_train_bpe.py **3 passed**（此前 2 failed），失败点曾是 `index 31: (b' ', b'd') != (b' a', b'nd')`。

## TinyStories 全量实测（train 2.12GB, vocab 10000）
| 指标 | 慢版本(max 扫描) | heap 版 |
|---|---|---|
| merge 阶段 | 16.7 s | 10.9~11.1 s |
| 总耗时 | 152.4 s | **286~298 s** |
| 峰值 RSS | 6.35 GB | **12.0~12.5 GB** |
| merges / 最长 token | 9743 / ' accomplishment' 15B | 一致 |
- **结论：merge 快了 33%，但总耗时与内存都翻倍 ⇒ 净退步**。根因是 issue ②（push 在最内层）：
  堆涨到千万级，每次 push/pop 约 25 次比较且 `Rev.__lt__` 是 Python 层调用；
  同时千万级存活对象让 CPython 分代 GC 反复遍历，这是总耗时翻倍的主因之一。
- 已达标：题目要求 TinyStories ≤30 分钟 / ≤30GB，当前 4.8 分钟 / 12GB 已过线。
  但 OWT（11GB、32000 轮）按此膨胀率会爆 100GB，② 必须修。
