## 讲解 find_chunk_boundaries（cs336_basics/pretokenization_example.py）
- 用户问这个函数怎么工作。已讲：等间距猜测 → 每次读 4KB mini chunk → `bytes.find` 找
  `<|endoftext|>` → 边界 = 猜测位置 + 找到的偏移；EOF 仍找不到则边界 = file_size；最后
  `sorted(set(...))` 去重。
- 关键语义：返回的边界指向特殊 token 的**首字节**，所以除第一块外每块以 `<|endoftext|>` 开头，
  保证不会跨文档 merge。
- 已知瑕疵：若特殊 token 横跨 4KB mini chunk 边界会被漏掉，切点顺延到下一个 token，
  不影响正确性（仍落在某个特殊 token 开头），只是分块略不均。
- 提醒过：返回块数可能少于 desired_num_chunks，必须用 `zip(boundaries[:-1], boundaries[1:])` 迭代。
- 仍遵守 AGENTS.md：只讲原理与方向，不改 train_bpe.py。下一步并行化由用户自己实现。

## 决策：暂不接入 multiprocessing 并行化
- 理由（已给用户分析）：TinyStories 已 2.54 分钟 / 6.35GB，远低于 ≤30 分钟 / ≤30GB 硬指标，
  并行化只省约 2 分钟且**不额外得分**（train_bpe_tinystories 只有 2 分，考的是一两句回答）。
- 更关键：OWT 的瓶颈是 merge（65499s / 65613s，占 99.8%），pre-tokenization < 113s，
  所以并行化对 OWT 也几乎无收益；OWT 必须靠 heapq + 惰性删除改 merge 循环。
- 建议优先级：① OWT merge 循环提速（阻塞项）② 填 log.txt 的 writeup 答案（4 分）
  ③ Tokenizer 类（19 分）④ 并行化（0 直接得分，有余力再做）。

## 已讲：merge 循环提速（heapq + 惰性删除）
- 定量定位：OWT 每轮 `max(pair_counts, key=...)` 扫描约 2M 条 ≈ 1.5–3 s，
  × 31743 轮 ≈ 13–26 h，与实测 18.2 h 吻合 ⇒ 这就是唯一瓶颈，pre-tokenization 仅 <113 s。
- 方案要点（只讲不写）：
  * Python 只有最小堆，用 `(-count, pair)` 取反；但 **tie-break 是「字典序更大者胜」，
    无法对 bytes 取反**，必须用自定义 `__lt__` 的包装类把比较方向反过来。
  * 惰性删除：count 变化时不修改堆内旧条目，只 push 新条目；pop 后校验
    `count == pair_counts.get(pair)`，不等则丢弃继续 pop。
  * 正确性前提：**每次 count 变化都必须 push**，否则真最大值可能不在堆里。
- 给出的不变量：① 每轮选中的 max count 单调不增（可断言）② 与慢实现在小输入上
  merges 逐条相同 ③ `uv run pytest tests/test_train_bpe.py -q` 三项仍 PASS。
- 次要瓶颈：`pair_to_ids` 的 set 维护（每轮 O(受影响 pre-token 数)），改完 heap 后再评估。

## 机器差异问题（用户质疑，已澄清）
- 本机 = Apple M5 Pro / 18 核 / 48 GB RAM。之前 log.txt 的 18.2h 是在 Windows 机器上跑的，
  两次计时不同机，绝对时长不能直接比。
- 但换机器救不了 OWT：① 那次用的是 **owt_valid（276MB）**，交付要用 owt_train（约 11GB，40 倍）；
  ② 18.2h / 12h 只差 1.5 倍，属于常数因子，而瓶颈是复杂度（每轮 O(pair 种类数)）。
  11GB 上 pair 种类会涨数倍 ⇒ 实际是几十到上百小时量级。
- 定案方法（约 2–4 分钟，不用跑满 18h）：`uv run python profile_bpe.py data/owt_valid.txt 32000`
  的第 [3] 步会直接测「一次 max() 多久」并外推到 31743 轮；注意它在第 [4] 步会跑完整 train_bpe，
  看完 [1]–[3] 就 Ctrl-C。
- 内存也可能成为墙：本机 48GB，OWT 限制 ≤100GB，2GB 语料已峰值 6.35GB，11GB 上需观察。
- 顺序结论：先 heap；OWT train 上 pre-tokenization 约 75 分钟，heap 修好后它才会变成瓶颈，
  那时再上 18 核并行。
